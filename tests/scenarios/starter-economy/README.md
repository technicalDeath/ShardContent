# Starter economy disposable scenario

This directory keeps the reviewed server probe and Navrey client drivers used for the September 28 economy rehearsals. The probe is test-only and must be loaded only into a disposable copy of the shard. It is not included in deployment or regular builds.

The recorded sessions used `work/alpha3-starter-economy-host` (isolated from the shared distribution) and ordinary test accounts. Each client had a separate working directory and absolute `cmd2.txt`, `client2.log`, `state2.json`, and `world2.json` paths. `paired_economy_cases.py` exercises six direct bound-item trade/vendor attempts, nested bound contents, ordinary two-way secure trade, and ordinary player-vendor intake. `transfer_matrix.py` seeds all 41 bound starter implementations and checks each direct secure-trade and player-vendor attempt, then uses the admin probe to confirm authoritative parent, vendor-stock and trade state. Pass `reuse` only when the same saved session has already emitted the full target list; this resumes the attempts without creating duplicates. The September 28 matrix used state/server invariants because refusal narration did not appear. The `craft`/`make`, `craftwood`/`makewood`, `craftcloth`/`makecloth`, and `crafttinker`/`maketinker` probe pairs seed bound iron, boards or cloth plus the owner-bound tool, then run stock Blacksmith, Carpentry, Tailoring or Tinkering recipe paths. `tailoring_live.py` handles the maker's-mark gump and checks cloth/Shirt inventory; `tinkering_live.py` checks the Tinker Tools target and ingot/Gears inventory after waiting out the client action delay. Navrey can observe inventory and answer server gumps, but its API does not select T2A item-list menus; test-only staff commands invoke the stock resource-selection and recipe paths, and this limitation is recorded in the feature audit. After the owner opens the vendor's See goods action, `vendor_withdrawal.py` retrieves the ordinary control item. `npc_sale.py` drives an ordinary client's live Blacksmith sell list and transaction. `npc_legacy_ward_sale_live.py` checks an unmarked Ward sale plus same-serial buyback while confirming the marked starter Ward is excluded; its `npcward` fixture places the test Blacksmith before adding the temporary Ward entry because world placement reloads vendor sell info. `scissor_conversion.py` seeds bound cloth/armor and ordinary cloth, checks direct scissors on bound items and ordinary cloth, then invokes the observed Salvage Bag context actions against bound contents.

`StarterEconomyProbe.csproj` compiles against the disposable host assemblies. Build with the disposable host path if it differs from the default: `dotnet build StarterEconomyProbe.csproj -p:ServerHostPath=<absolute-disposable-host>`. Add its output to that copy's assembly list only. The fixture's `seed`, `transfers`, `salvage`, `npc`, `npcward`, `craft`, `make`, `craftwood`, `makewood`, `craftcloth`, `makecloth`, `vendor`, `verify`, `inspectward`, `trim`, `delete`, and `cleanup` commands create/delete test characters and world items. `npc_sale.py` opens the live Blacksmith sell list, confirms bound starter ingots are omitted while ordinary ingots are listed, then completes the ordinary sale. Cleanup removes only known synthetic player serials and the fixture characters named `StarterSalvage`, `StarterMatrixA`, `StarterMatrixB`, `StarterCraft`, `StarterCarpenter`, `StarterTailor`, and `StarterWardSale`, plus vendors they own and the named test Blacksmith; review its source and confirm the disposable save before reuse.

`inspectward <player-serial>` reports the live backpack enumeration and actual Blacksmith sell-info predicates for the Ward fixture; use it after a failed or empty sell-list interaction to distinguish fixture/setup state from production eligibility.

`scissor_conversion.py` places its test character at the Britain forge/anvil station and seeds a test Tongs tool so the stock Salvage Ingots action can run. The driver records the observed context entries, returned outputs and retained bound items. Run each client driver with the repository's bundled Python runtime and the absolute workspace root as its single argument. Each driver uses bounded waits and checks resulting client state. The server-side probe is needed to verify vendor stock and containment because client command delivery alone is not evidence of a successful transfer.

Current craft probe actions also include `craftleather`/`makeleather`, `craftbowyer`/`makebowyer`/`makearrow`, `craftscribe`/`makescribe`, `craftalchemy`/`makealchemy`, and `craftcook`/`makecook`. `craft_families_live.py`, `craft_bowyer_live.py`, `craft_remaining_live.py`, and `craft_cooking_live.py` exercise those stock recipe paths. The UOR Runebook recipe creates stock `Runebook` graphic `0x0EFA`, which this client labels “spellbook”; the driver matches the client label and the staff callback reports the recipe type. Bowyer's stock Shaft resource selection must use `Board`; the earlier callback using `Log` failed without consuming its bound board. `tinkering_conversion_live.py` crafts normal Scissors from bound iron and verifies stock Scissors refuses bound StarterCloth without consuming it.

`craft_output_transfer_live.py` uses separate seller, buyer and staff role directories to create ordinary Scissors from bound iron, trade the output between ordinary clients, return it, and add it to a player vendor. Run it once with a fresh test account/character and empty fixture inventory; the probe seed command uses the first matching bound stack in the backpack.

`npc_tinker_buyback_live.py` creates one stock Tinker NPC adjacent to a fresh test character, uses an ordinary Scissors output from bound iron to exercise the stock sell list, sale and NPC buyback, and records both gold changes and the repurchased item. The test-only probe removes the specifically named Tinker in `cleanup`.

`npc_tailor_buyback_live.py` creates an ordinary Shirt through the stock Tailoring recipe from bound cloth, then verifies the stock Tailor's live sell list, sale, same-serial buyback and both gold changes. It uses a fresh client role because the probe chooses the first matching bound cloth stack.

`wardscan` reports aggregate loaded-world Ward counts by starter marker and container/world location without account identifiers. `legacy_ward_live.py` seeds an unmarked ordinary Ward, verifies real paired-client secure trade and player-vendor intake, and uses `item` for authoritative vendor-stock state. Its test fixture and test characters are removed by the probe's `cleanup`; save/restart recount is required before claiming persisted no-op behavior.
