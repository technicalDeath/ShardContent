# Alpha 3 Phase G: Starter combat gear and consumables readiness

**Decision:** Ready for Alpha 3 enablement, with `alpha3StarterCombatGear` still disabled (the validator hard-rejects it outright regardless; see Gate and validator). This closes feature readiness only; the combined Phase L activation decision remains outstanding.

## Reused accepted evidence

- The prior package planner/synthetic issuance and 41-type direct bound-transfer matrix ([starter audit](Alpha-3-Starter-Package-Audit.md#archetype-package-selection-and-stock-overlap)) verified the *old*, now-replaced design (custom package selection, ~20 bound combat-gear types). It is superseded, not reused: the 2026-09-28 rulings (Contract-Review.md G-1 through G-9) replaced that design with plain stock item types, newbied only. The 27-type bound-item and vendor-eligibility matrices in `StarterSaleEligibilityMatrixTests.cs`/`StarterDeathRuleTests.cs` no longer include G's former types.
- Phase E's E-MURDERER live case (a plain, non-bound Newbied `Katana` lost on a murderer's death) is reused as the evidence for G-MURDERER: G's combat gear uses the identical `LootType.Newbied`, non-`Nontransferable` classification, going through the identical unchanged `Item.OnInventoryDeath`/`OnParentDeath` check (`CheckNewbied() && !parent.Murderer`). See [starter audit](Alpha-3-Starter-Package-Audit.md#owner-rulings-and-phase-e-closure--september-28-2026).
- The stock trade/vendor/salvage/BOD guard mechanism (`Item.Nontransferable`, `OnDroppedToMobile`/`OnDroppedInto`/`OnDroppedToWorld`) is unchanged stock engine code, already traced and reused from prior phases.

## Current-source review

Stock `CharacterCreation.cs`'s `EquipItem`/`PackItem` helpers stamp every piece of creation-time gear `LootType.Newbied` whenever `!Core.AOS` — true for this shard's UOR era — with no shard involvement. Confirmed for this shard's actual `Warrior`/`Mage`/`Blacksmith` profession definitions (`ModernUO/Distribution/Data/Professions/None/prof.txt`): the Warrior profession's `GiveProfessionItems` branch matches `profession.Name.ToLowerInvariant() == "warrior"` and grants the full 7-piece studded suit; Mage and Blacksmith match no profession branch and fall through to shirt/pants/shoes only, with all their gear coming from per-skill `AddSkillItems` grants instead. Human weapon types (`SwordsWeapon`→Katana, `MacingWeapon`→Club, `FencingWeapon`→Kryss, `RangedWeapon`→Bow) match exactly what the prior custom design hand-picked. Stock's `Spellbook` constructor unconditionally sets `LootType.Blessed` (not `Regular`), so the auto-newbie stamp never touches it — confirmed both by source and live.

`StarterCombatIssuance.Issue()` is now five narrow, idempotent top-ups/patches (arrow and reagent quantity raises; archer-leather, Parry-shield and bandage-fallback patches for the two/three specific gaps stock leaves empty), gated on `Alpha3StarterCombatGear` and a per-character account tag. It never deletes or replaces anything stock already granted. `StarterCombatGear.cs` and `StarterCombatConsumables.cs` (13 bound types: weapons, armor, shield, spellbook, bandage, arrow) are deleted.

The vendor-sale guard (`GenericSell.cs`'s `NontransferableItemPolicy.ContainsVendorRestricted`, used by `GenericSellInfo.IsSellable`/`IsResellable` and `PlayerVendor.OnDragDrop`) now also blocks `LootType.Newbied` items, alongside the existing `Nontransferable` check — closing the resale faucet that newbied-only binding would otherwise reopen, without touching trade (`PlayerMobile.CheckContentForTrade`), salvage (`SalvageBag.CanResmelt`) or BOD (`SmallBOD.EndCombine`), which stay keyed on `Nontransferable` only. Broadening to also cover `LootType.Blessed` was considered (the spellbook gap) and rejected: `Blessed` is set unconditionally by roughly 200 unrelated stock item types (veteran rewards, quest items, holiday content), so blocking it shard-wide would be a large, unrelated economy change for one item's few-gold resale value — an owner-confirmed accepted residual instead.

## New verification

Full Shard suite: 255/255 (verification run `20260928T190353213Z-21b497`). UOContent `StarterBoundVendorTests`: 11/11 (8 existing + 3 new, against real `PlayerVendor`/`GenericSellInfo`/`PlayerMobile`/`SalvageBag` objects; run `20260928T184521390Z-b3e229`, prior to the later spellbook-related revert, which the guard tests are unaffected by).

Live: seven fresh ordinary accounts on disposable host `phase-g`, using the normal Navrey `createcharacter` packet with a test-only in-memory flag override (`tests/scenarios/starter-combat/StarterCombatFlagOverride.cs` — flips `ShardRulesConfiguration.Settings.FeatureFlags.Alpha3StarterCombatGear` after boot, never touches disk or `Validate()`). Warrior, Mage, Archer, Melee+Parry, a two-weapon hybrid, and two Archery/Swordsmanship orderings all produced correct, server-verified (`StarterCombatInspect`) inventories: stock weapons/armor/bandages kept as-is and Newbied; archer leather, Parry shield and bandage-fallback patches applied exactly where stock has a gap; arrows always raised to 100 whenever Archery was selected, regardless of ordering. A live ordinary death (`starter_combat_death_live.py` against a Melee+Parry character) confirmed the Newbied bandage stack and shield survived while the Nontransferable Backpack Ward also survived, unaffected by G. Full details, including named gaps in the live pass (no direct "Archery-as-secondary" repro, no live murderer case, no live vendor click-through), are in the [starter audit's Phase G section](Alpha-3-Starter-Package-Audit.md#owner-rulings-and-phase-g-closure--september-28-2026).

## Gate and validator

Source and deployed `alpha3StarterCombatGear` are both `false` (confirmed via `Get-ShardStatus.ps1` after this pass). `ShardRulesConfiguration.Validate` still hard-rejects this flag outright (H-6, unchanged) — it cannot be set `true` in `shard-rules.json` even on a disposable host; `Load()` throws before the server starts. This is why live gated testing needed the in-memory test-only override rather than a config change.

## Readiness limits

- Dropping the custom package-replacement system surfaced pre-existing stock duplicate grants (e.g. a Warrior gets two Katanas and two Bandage stacks, from Tactics' and Swords'/Healing's independent skill-item grants) that the old custom code silently deleted. Named, not fixed — the owner's G-1 ruling explicitly chose to accept stock behavior over reintroducing that cleanup.
- The mage Spellbook stays stock `LootType.Blessed` (owner ruling) and is not covered by the vendor-sale guard; it remains vendor-sellable. A named, accepted residual, not a gap.
- G-5's live cases didn't reproduce "Archery selected as a genuinely secondary skill" (both orderings tried resolved Archery as the strongest selected combat skill); the fix is unconditional by source inspection regardless.
- No live murderer-death case for G's own item instances (reused Phase E's identical-code-path evidence instead); no live vendor-sale packet click-through (relied on UOContent.Tests engine-level proof instead). Reasons and reused-evidence citations are in the audit's Limits section.
- `StarterCombatIssuance.Issue()`'s full integration behavior has no shard-level xunit coverage, matching the prior implementation (no live `PlayerMobile`/`World`/`Account` environment in `BritanniaRenaissance.Content.Tests`).
