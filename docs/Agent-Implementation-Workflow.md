# Efficient implementation workflow

Use this workflow for ShardContent and its ModernUO integration. Read the workspace `CLAUDE.md` and the skills in the workspace `.claude/skills/` first (the earlier Codex `.agents` skills are archived under `archive/codex-agent-files-2026-09-28/`). The running shard is a local development environment; there is no live production shard. This allows ordinary gameplay tests and planned restarts on the local host. Its saved world and accounts are still shared mutable data, so keep one writer and make a snapshot before tests that could damage or irreversibly change them. This document governs how to group work and verification, not what a phase is allowed to ship.

## What the Alpha 3 work taught us

- **Working well:** feature flags and validation gates kept unfinished systems disabled; focused tests and real client checks found integration gaps that source inspection could not; narrow ModernUO hooks kept shard policy in ShardContent.
- **Taking too long:** starter materials were added across separate small passes, with three scratch-server runs for one related package family. Other starter items received separate issuance, death, persistence, transfer, and client rehearsals. Each run repeated assembly setup, process startup, account cleanup, shutdown, and documentation. Because this is a development shard, disposable copies were also used for checks that could have run on the local host with dedicated test accounts. These are useful checks, but the repeated setup was avoidable.
- **Redundant:** the same overall test suite, source-flag review, scratch-host restoration, and long status paragraphs were repeated after small increments. Feature-specific results were copied into the roadmap, starter audit, and orientation skill. This made the durable documents harder to scan and increased the chance that their status would drift.
- **Limits of this assessment:** there is no measured time breakdown. The conclusions come from the documented sequence of implementation and scratch runs, not a timing benchmark.

## Plan a coherent pass

For Alpha 3, the owner has selected a one-feature-at-a-time sequence. Finish the selected letter's bounded acceptance work and readiness record before starting another feature; move on only after that review or an explicit owner change/suspension of the order. A feature-ready result does not complete or activate Alpha 3. Status questions and corrections steer the selected work unless the owner explicitly pauses or replaces it.

For Alpha 3, use `Alpha-3-Feature-Enablement-Plan.md` as the single active feature order and task ledger. `Alpha-3-Implementation-Log.md` is historical. `tools/Get-Alpha3WorkQueue.ps1` reads the new plan. The roadmap defines scope; feature audit/rehearsal documents hold evidence; skills hold durable operational knowledge. Do not copy each test count into all four places. Historical passing evidence can be reused unless affected source, data or configuration changed; record the reason when a rerun is needed.

1. Read the applicable skills and repository instructions, check status/remotes for each repository to be touched, and inspect active source flags. Select the current lettered feature and group its related cases so fixtures and verification can be reused; do not make each item, recipe or assertion its own deployment batch. For starter packages, map every relevant stock grant and interception point before editing.
2. Write a short acceptance matrix before implementation: expected behavior, persistence boundary, economy/transfer boundary, ordinary client path, and release gate. Mark cells that can be covered by source inspection, automated tests, the local development host, or a disposable copy. Include only checks relevant to the change.
3. Implement the entire coherent pass together: source hook, policy, configuration/validation, item provenance, and any necessary targeted tests. For a one-line or low-risk request such as adding scissors to starting gear, make the change, run the smallest useful check, and move on. Do not turn an isolated item into repeated full lifecycle rehearsals unless its binding or economy rules require them.
4. Run fast feedback after the pass: formatting/compilation, focused tests for the changed behavior, and one full content suite at a milestone or before release. A failed check justifies a repair and rerun of the affected scope. Do not rerun the full suite after each adjacent file edit.
5. Batch related gameplay checks into one local-host session by default. Stop the existing server once, deploy the coherent pass, restart once, and run the planned matrix with dedicated test accounts. Save/restart only for a persisted-state check. Reuse that session for several related starter categories rather than booting once per category. Use a real client for behavior that depends on packets, UI, targeting, or ordinary player interaction; a synthetic probe is sufficient for narrower server-only invariants. Use a disposable copy when a test needs a clean world, risky migration, destructive world generation, or a rollback that would discard other development state.
6. Record results once in a focused evidence document. Keep the roadmap at phase-level status and link to evidence. Update a skill only for durable layout, integration, runtime, or safety knowledge; do not copy each task's test log into it.

## Verification by change size

| Change | Immediate check | Batched or release check |
| --- | --- | --- |
| Text, roadmap, or simple configuration wording | Diff and relevant search | None unless meaning depends on runtime configuration |
| Small isolated code change | Build or focused test that exercises the changed path | Existing phase matrix if gameplay boundaries are affected |
| Related feature family | Build and targeted tests after the group | One local development server/client matrix for grants, consumption, transfer, death, and persistence as applicable |
| Engine hook, save format, economy path, or phase activation | Focused test plus full content suite | Local-host or disposable save/restart and ordinary-client matrix, chosen by data risk; inspect flags, deployed pin, and runtime logs |

## Boundaries that batching must preserve

- Never build/copy over assemblies loaded by the local server or start another writer against its save. Check loaded modules as well as the listener. Use the build option that skips content deployment while it is running. Plan one stop/deploy/restart cycle per coherent batch.
- ModernUO project files write to `Distribution` by default. While that host has assemblies loaded, pass an isolated absolute `OutDir` to every ModernUO build/test invocation. Its test fixture reads runtime `Data/skills.json`; copy that file into the isolated output's `Data` directory before test execution. Tests constructing NPCs can additionally require `Data/npc-speeds.json`; tracking and other body-type tests require `Data/bodyTable.cfg`. Set `MODERNUO_TEST_DATA_DIR` to the local UOData directory when map/tile data is needed. Missing fixture data can produce misleading functional failures, so choose small server-logic tests when those assets are irrelevant.
- ShardContent references ModernUO binaries from `ModernUOPath/Distribution` rather than its project source. If that distribution is older than current ModernUO edits, stage the isolated `Server.dll`, `UOContent.dll`, `Logger.dll`, and code-generated-events annotations in a scratch `Distribution` layout and pass `-p:ModernUOPath=<scratch root>` with `-p:SkipShardContentDeploy=true`. This gives a current cross-repository build without replacing loaded assemblies. For UOContent tests that need map/tile data, set `MODERNUO_TEST_DATA_DIR` to the local UOData directory for that test process.
- Keep unready source feature flags off and retain validation blockers. A test-only runtime override is acceptable when isolated to the test session and restored afterward. Do not silently activate an unfinished phase.
- Use dedicated test accounts and clean up test objects. Snapshot the local save before tests that may irreversibly alter existing state. Use a disposable copy when cleanup or snapshot restoration cannot safely isolate the test.
- Stop a batch when a failed invariant could corrupt subsequent evidence. Fix it, reset the test state if needed, then continue the remaining matrix. A single long run is useful only while results remain attributable and reproducible.
- Prefer a small number of clear checkpoints: coherent implementation complete, automated checks passed, runtime matrix passed, and release decision. Report blockers and evidence at those points instead of narrating every edit.
- When several services attach to one ModernUO callback field, review every assignment site before the client pass. Automatic `Configure` discovery and bootstrap calls can run in different orders; a single late `=` can erase earlier `+=` observers. The Alpha 3 creation packet matrix caught this despite a passing unit suite. Check the final observer behavior through one ordinary client creation/death batch.

## Next Alpha 3 pass

### Prepare a finite verification campaign

Before the next runtime deployment, list the remaining distinct behaviors in the existing feature evidence document. For each, identify its entry point, implementation/serializer, exact expected result, test role, and whether it needs a restart. Map accepted evidence to those behaviors first. Exhaustive type matrices can run as automated checks; a representative ordinary-client route can cover shared behavior only when the source mapping is explicit. Distinct packet handlers, economy hooks, serialization formats and failure paths still need their own checks. Do not silently reduce roadmap acceptance requirements.

Prepare the whole selected feature's source changes and test fixture together, including seed/reset, inspection, cleanup, recipe inputs, expected consumption and post-restart assertions. Check recipe requirements in source before launch. Run fast focused checks during implementation; defer the expensive runtime campaign until its fixture is ready. A broad open checklist entry is not an instruction to repeat every lifecycle for every subtype. `Get-Alpha3WorkQueue.ps1 -Section 'K. Permanent outdoor Hot Zones'` narrows a read-only view without changing status or authorizing a feature switch.

Use one host session for the prepared cases and reset test-owned state between them. Seed all independent persistence states, explicitly save, restart once, and assert them together where possible. Repeated restart sequences remain necessary when the requirement itself is multi-cycle behavior. Adding a Python assertion or changing test data does not require reloading unchanged server assemblies. Rebuild/restart only for changed loaded code/configuration, a required persistence boundary, or a documented unrecoverable fixture state. Record the reason for each restart in the campaign notes.

Clean test-owned fixtures once at campaign teardown where their isolation permits it. Trigger an explicit save instead of waiting for scheduled autosave. Keep the admin client connected until it has sent `[Save`, and await disk publication before stopping the server. Use `tools/save_test_world.py` with its explicit session paths; the `navrey-test` skill documents the command. A server started with `.claude/scripts/Start-DevServer.ps1` also accepts console `save` through `Send-DevServerCommand.ps1`. Ordinary clients can stop first, but stopping the only command-capable admin first makes saving unnecessarily difficult. A console `save` is equally valid when the server has an attached console. `[Restart` is not a cleanup/save API.

When a planned case fails, repair that behavior and rerun affected cases; reuse unaffected results. At campaign end, replace vague residuals such as "broader coverage remains" with named uncovered behaviors and their reason. Do not keep adding recipes or vendor types solely because more examples exist. Prepare additional cases within the selected feature while its runtime campaign is pending, leaving their evidence cells open.

Follow the alphabetical order in `Alpha-3-Feature-Enablement-Plan.md`; do not maintain another task queue here. For each feature batch, record the exact outstanding scenarios before restarting a server, then close those cells with evidence or name the remaining failure. An open-ended phrase such as “broader checks remain” is not an executable next step.

Use `tools/Invoke-AgentVerification.ps1` for current-source automated checks. It encapsulates isolated output, reference staging, fixture data, test-result validation and a shared build lease. Keep one coherent test session for related client scenarios, following the save/process rules above. Reusable probe source and scenario instructions belong in the owning repository; generated assemblies, credentials and raw client logs stay in ignored scratch paths. If a probe is temporary, preserve enough scenario instructions to reproduce its evidence without rediscovering setup.
